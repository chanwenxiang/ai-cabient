- **修复建议**: 把 `doAddRestock` 既有批次路径改成与 `doRestoreToBatch` 同款两段式：`increaseQuantityAtomic(lotId, command.quantity())` + `updateStatusAndSlotById(lotId, resolveLotStatus(...), slotPatch)`（新批次路径保持 INSERT 不动）。

### MA-177（P3）批次建档无唯一键：R18-4 的 upsert 只收口了聚合表，`device_sku_lot` 并发建档会产生重复批次行

- **复现路径**: `services/trade-service/src/main/resources/db/migration/V24__inventory_lots_phase_a.sql:10-25`——`device_sku_lot` 建表仅有普通索引 `idx_lot_device_sku (device_id, sku_id)`，**无 (device_id, sku_id, batch_no) 唯一约束**；全迁移集 grep 无任何 `UNIQUE` 落在该三元组上。应用侧两条建档路径（`InventoryLotService.java:337` restore 回库新建、`:383-395` restock 新建）都是 find→INSERT 形态、无 DuplicateKey 兜底。R18-4（51916f22）把「建档竞态」修成了 `upsertIncreaseQuantity`（`DeviceSkuInventoryMapper.java` 尾部，ON CONFLICT (device_id, sku_id)），**但只覆盖聚合表**。
- **后果**: 锁失效/多副本下两实例同批建档 → 两行同 (device, sku, batch)、各自 lotId。量不丢（`sumSellableQuantity` 与 `findAllByDeviceIdAndSkuIdAndBatchNo` 都按行集求和），但 `findByDeviceIdAndSkuIdAndBatchNo`（orderByDesc(updatedAt) 取第一条）变成非确定性读，restore 的 `increaseQuantityAtomic` 打在哪一行不可预期；同族地，`syncAggregateInventory`（:542-562）对聚合表仍是 find→实体 save，两副本同时首建聚合行时后到者吃 DuplicateKeyException（500 回滚，可重试，无资金损失）。
- **修复建议**: 新迁移为 `device_sku_lot` 补 `(device_id, sku_id, batch_no)` 唯一约束（先跑存量重复行探针，重复行先合并工单），建档路径改 `INSERT ... ON CONFLICT DO UPDATE quantity = quantity + EXCLUDED.quantity` 同款 upsert。
- **需拍板**: 补唯一键涉及存量合并，见「需拍板」节。

### MA-178（P3）预授权第二来源 `device.deposit_cents` 不在 S12 天花板内，且穿透「0=关闭预授权」语义

- **复现路径**:
  1. 读侧：`services/trade-service/src/main/java/com/aicabinet/trade/service/ConsumerPreauthService.java:67-73`——`resolvePreauthCents` 的**第一优先分支**按 `device.getDepositCents() > 0` 直接返回，先于 74-92 行的 DB 键分支；因此既不受 `CommissionParamBounds.PREAUTH_CENTS_CEILING`（100 万分）约束（该分支无任何上界），也不受 80febfeb 归位的「`checkout.preauth_cents=0` ⇒ 关闭预授权」语义约束——运营把全局配 0 关预授权后，凡设了押金金额的设备仍照常冻结。
  2. 写侧：`services/trade-service/src/main/java/com/aicabinet/trade/service/OpsDeviceAdminService.java:607-609`——`UpdateDeviceRequest.depositCents` 只钳负数（<0→0），**无上界**；配 ¥1000 万的"押金"会被原样接受，开门预授权按它走（该设备余额不足者一律 412，方向是拒服务不是资损）。
- **定性**: 该分支为 f030f09f 时代既有代码（先于本审计区间），S12/80febfeb 修的是同函数的 DB 分支——属「同族字段残留」而非新引入回归。资损方向为 fail-safe（多冻 → 拒开门），但「0=关闭」语义被设备级配置静默穿透与 S12 的拍板口径不同源。
- **修复建议**: 写侧给 deposit_cents 挂同一天花板（`PREAUTH_CENTS_CEILING`，单源 CommissionParamBounds）；读侧设备分支超天花板回落 DB 默认并 WARN；「0=关闭 vs 设备押金优先」的优先级写进两处 javadoc 并拍板留痕。
- **证据**: `git log --all -S "getDepositCents() != null && device.getDepositCents() > 0"` → f030f09f（区间外）；9d5c724f/80febfeb diff 均未触及 :67-73。
