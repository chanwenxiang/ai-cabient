## 1. 业务场景

我方主营智能开门柜（无人零售柜）的研发、生产与场地运营。柜机布设于办公室、餐饮店、园区等
封闭/半封闭消费场景，单次消费客单价为小额商品金额。

**消费者完整链路：**

```
微信扫码柜机二维码 → 进入「叮当小柜」微信小程序 → 开通微信支付分（服务维度长期授权）
→ 扫码开门 → 随心取货 → 关门 → 按实际取走的商品自动扣款 → 收到扣款通知
```

**核心特征（与「预充值/预付费」的本质差异）：**

| 维度 | 传统预充值零售柜 | 我方「先享后付」 |
|---|---|---|
| 支付时点 | 开门前充值 | 关门后按实际商品结算 |
| 金额确定性 | 预付固定额度 | **动态金额**：开门时不确定，关门后按实际取走商品计费 |
| 资金占用 | 用户需先付费 | 用户无需预付，信用准入 |
| 坏账承担 | 商户预充值余额 | 商户承担（微信侧提供信用评估与催收链路） |

## 3. 技术接入方案

### 3.1 整体架构

```
微信小程序（叮当小柜，AppID wx9025aa7a38f11a95）
   │  ① 申请开通授权
   ▼
trade-service（我方服务端，直连模式，1700080722 自有证书与 APIv3 密钥签名）
   │  ② POST /v3/payscore/permissions      → apply_permissions_token
   │  ③ 小程序 wx.openBusinessView(businessType=wxpayScoreEnable, extraData{apply_permissions_token})
   │  ④ 用户在微信授权页确认 → 微信异步通知 authorization_code + user_service_status
   │  ⑤ 开门：POST /v3/payscore/serviceorder (need_user_confirm=false, risk_fund=ESTIMATE_ORDER_COST)
   │  ⑥ 关门：POST /v3/payscore/serviceorder/{out_request_no}/complete (post_payments 逐件商品)
   ▼
微信支付分 → 自动扣款 → 扣款结果回调
```

**接口路径说明**：我方按【直连】普通商户模式接入，使用直连版接口路径
（`/v3/payscore/permissions`、`/v3/payscore/serviceorder`、`/v3/payscore/serviceorder/{no}/complete`），
**不传 `sub_mchid`**。
依据：官方《接入支付分须知》表格「普通商户、特约子商户 →【直连】普通商户模式 → 需确认和免确认模式」。

### 3.2 授权开通（服务维度长期授权）

| 项 | 内容 |
|---|---|
| 服务端调用 | `POST /v3/payscore/permissions` |
| 请求体 | `service_id`、`appid`、`authorization_code`、`notify_url` |
| 应答 | `apply_permissions_token` |
| 小程序拉起 | `wx.openBusinessView({ businessType: 'wxpayScoreEnable', extraData: { apply_permissions_token } })` |
| 授权结果 | 微信异步通知 `authorization_code` + `user_service_status`（`USER_OPEN_SERVICE` / `USER_CLOSE_SERVICE`）→ 我方激活/失效授权状态 |

> ⚠️ 授权页在**用户手机上**由微信完成核身，与柜机是否具备人脸识别硬件无关。
> 我方柜机无刷脸设备，授权环节不依赖柜机硬件。

### 3.3 开门前创单（信用评估）

| 项 | 内容 |
|---|---|
| 接口 | `POST /v3/payscore/serviceorder` |
| 关键参数 | `out_request_no`（我方订单号）、`service_id`、`appid`、`service_introduction`、**`need_user_confirm=false`**、**`risk_fund=ESTIMATE_ORDER_COST`**、`time_range`、`goods_tag` |
| `need_user_confirm=false` | 对应【免确认订单模式】：用户已做服务维度长期授权，创单阶段不再要求用户逐单确认 |
| `risk_fund` | 风险金上限，微信侧按场景规则校验 |

> 🔴 **待确认项（已列入申请邮件必问项）**：【无人零售】场景申请的 `service_id` 是否自带免确认接口权限。
> 官方《开发接入准备》说明「接口调用权限与 service_id 相关……只有特定场景下的 service_id 才有权限调用
> 【免确认订单模式】接口」。若该场景暂不开放免确认权限，我方将改为【需确认模式】上线运营
> （创单后由用户拉起确认页），届时接口契约与交互图需同步调整。

### 3.4 关门后完结（动态金额结算）

| 项 | 内容 |
|---|---|
| 接口 | `POST /v3/payscore/serviceorder/{out_request_no}/complete` |
| 请求体 | `service_id`、`appid`、`out_request_no`、`completion_time`、**`post_payments`（逐件商品：sku_id / sku_title / amount / quantity）** |
| 金额来源 | 与开门前的商品价目**同源同价**，取自柜机识别到的实际取走商品 |
| 后续 | 微信自动发起扣款；失败按微信侧策略重试与催收；扣款结果回调我方更新订单状态 |

### 3.5 订单状态机

我方订单状态与微信支付分状态对应：

```
CREATED（已识别/待开门）
  → DOING（开门中，货舱已解锁）
    → USER_PAYING（关门后完结中，等待扣款）
      → DONE（扣款成功）
      → FAILED（扣款失败，转微信侧催收/重试链路，我方保留申诉入口）
```

### 3.6 回调接口

| 回调 | 内容 | 我方处理 |
|---|---|---|
| 授权结果 | `authorization_code`、`user_service_status` | 激活/失效支付分授权状态 |
| 服务订单状态 | 支付分订单状态变更 | 同步订单状态 |
| 扣款结果 | 扣款成功/失败 | 更新订单终态、通知用户 |

回调地址需公网可达，并在微信商户平台配置。

### 3.7 商品识别与计费

- **SKU 识别**：柜机侧通过视觉识别/电子价签获取实际取走商品（我方以 RFID/视觉等柜机侧识别结果为准）。
- **计费规则**：按实际取走商品金额计费；开门时金额不确定（动态金额），关门后按实际商品列表结算。
- **异常**：识别结果与用户实际取走不一致时，走订单申诉/客服核销链路。

## 5. 双渠道一致性

同一柜机二维码，**微信与支付宝双渠道并行**（落地页按 User-Agent 分流）：

| 渠道 | 产品 | 承载 |
|---|---|---|
| 微信 | 微信支付分 · 无人零售 · 免确认 | 微信小程序内 `wx.openBusinessView` 授权页 |
| 支付宝 | 信用代扣（单次代扣 / 芝麻先享动态金额，产品选型待支付宝侧确认） | 支付宝 App 扫码 → 服务端落地页授权 → 唤起支付宝开通页 |

两套协议与状态机独立存储（**不共用同一协议号列**），互不影响，任一渠道不可用时另一渠道仍可服务消费者。
