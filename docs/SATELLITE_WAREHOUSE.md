# 分仓补货落地（对照 easygo，小步）

> 来源：2026-10-04 会话（补货员与公司不在一地、仓在补货员附近）。  
> **不要**把商户要货当天作业入口；**不要**一次抄旧系统整包。

## 现场口径（easygo）

1. 仓跟人走：补货员/线长手机号绑一个分仓。
2. 采购进自己的仓：申请 → 审核 → 货送到该分仓。
3. 每天补柜不申请要货：缺货量 = 货道额定 − 当前库存；到柜开门改库存。
4. 月结：该仓应有 vs 实盘 vs 本月上柜件数。

## 推荐顺序（仍按此写，禁止并行铺开）

1. **人绑仓**：仓库 `manager_user_id`；后台编辑仓库时选择负责人。
2. **采购进分仓**：收货仓默认负责人的仓；无负责人则禁止当日常入口。
3. **日常从仓到柜**：缺货建议 → 出库 → 补货任务；无出库不「去补货」（闸门已在）。
4. **月结一张表**：应有 = 上期 + 采购入库 + 调入 − 调出 − 上柜 − 损耗；再对实盘。

要货只留给商户喊缺货，不是补货员每天入口。

## 保存约定（人绑仓）

- 后台编辑仓库会带 `managerUserId`：正数绑定，`0` 或清空下拉则解绑。
- CSV 导入不带该字段 → 后端当作「不改」，避免把已绑人冲掉。

## 保存约定（采购进分仓）

- 指定 `warehouseId`：仓必须存在且 `manager_user_id` 非空，否则中文错误拒绝。
- 不指定仓：取当前操作人作为负责人的第一家 `ACTIVE` 仓；没有则拒绝。**禁止**再落到无主默认中心仓。
- 后台新建采购下拉只列已绑负责人的仓；默认当前登录人的仓，否则当前筛选仓，再否则第一家有负责人的仓。
- 补货员小程序「采购入库」：`GET/POST /api/v2/merchant/satellite-purchase/*`，仓强制为当前人 `manager_user_id` 的 ACTIVE 仓；无仓拒绝。要货入口仍独立。
- 待收货单可在「单据」里确认收货（批次/到期日必填），库存入本人分仓；不能收别人的仓。

## 保存约定（日常从仓到柜）

- 规划补货路线生成出库：未指定仓时用柜机 `home_warehouse_id`；同一路线柜机必须同一所属仓。
- 仓必须已指定负责人，否则不能日常出库。**禁止**落到无主默认仓。
- 商户「缺货巡柜」只看缺口，不把要货当天作业入口；要货入口仍在柜机详情。
- 补货员日常采购走「采购入库」，不要货。

## 保存约定（月结一张表）

- 后台「库存与盘点 → 月结」：须选仓库和月份（上海时区）。
- 应有不含盘点调整；损耗单独列；实盘来自本月最近一次 COMPLETED/ADJUSTED 盘点。
- 只计件数，不写金额，不进结算 GMV。

## 月结对齐财务口径（2026-10-13 用户拍板）

**盘点节奏**：月末最后一天全盘（如 31 号），把柜机货全部拉空一起盘总库存——实盘来源可靠，每月 1 日自动生成上月月结草稿时取到的就是月末完成的盘点。

**字段对照（财务现行 18 列 ↔ 系统字段）**：

| 财务字段 | 系统字段 | 备注 |
|---|---|---|
| 库存月份 / 分仓名称 | yearMonth / warehouseName | 已有 |
| 商品sku / 商品全称 | skuId / skuName | 已有 |
| 上期盘点 | openingQty | 已有 |
| 采购入库 | purchaseInQty | 已有（satellite-purchase） |
| 仓库调入 / 仓库外调 | transferInQty / transferOutQty | 已有 |
| 机器补货 | restockQty（上柜） | 已有 |
| 摇机损耗 / 过期损耗 / 客情用水 / 费用抵扣 | **待拆：损耗单列 → 四列** | 过期损耗可从过期调整流水归集；其余见下 |
| 仓库应有 | expectedQty | 公式加扣四类损耗 |
| 实际盘点数 | countedQty | 已有（月末全盘） |
| 差异 | gapQty | 已有 |
| 单价 | **待加列**（= 目录采购成本） | 现在只落金额不落单价 |
| 金额 | gapAmountCents | 已有 |

**损耗四类的来源设计**：
- **客情用水**：不走手工补录——补货任务加「补货目的」类型（正常补货 / 客情用水），从分仓出库时带类型，月结按类型归集出「客情用水」列（例：5 月 1 日给某柜补客情水 20 瓶 = 一条客情类型的补货任务）。领用可追溯，月末自动汇总。
- **过期损耗**：从已有过期/盘点调整流水自动归集。
- **摇机损耗 / 费用抵扣**：财务在月结草稿阶段手工补录（草稿行可编辑，生成后、审批前填写）。

**自动生成**：xxl-job 托管任务 `warehouse-monthly-close`（每月 1 日 02:00，上海时区），为每个 ACTIVE 仓生成上月草稿；已审批（APPROVED）仓/月跳过，DRAFT 重生成（幂等）。**系统只算差异明细（件数+金额），不做任何扣款动作**——财务核对后线下实际扣钱；CLAIM 处置进索赔台账仅为挂账。

**与旧系统（easygo）对照**：旧系统 opt_stock_record_daily 按 SKU×天记应有/实际，盘点=改实际数，差异线下算、无自动扣款——本方案保留「线下扣钱」口径，差异计算与台账化比旧系统强。

## 要货下线、自主补货上线（2026-10-13 用户拍板，修正上文「要货只留给商户喊缺货」等旧结论）

**拍板**：要货（申请→运营审批）整链下线——商户端页面/入口、后端 6 端点、`merchant_replenishment_request(_line)` 表（**V346** DROP）全部删除。理由：补货员异地有自己分仓，日常补货不该「向仓库喊一声」走审批；旧系统（easygo）也无要货概念。

**替代能力 = 自主补货**：`POST /api/v2/merchant/replenishment/self-initiate`（权限沿用 `merchant:replenishment:request`），无审批直接生效：校验柜机 `home_warehouse_id` 负责人 → 建路线+PENDING 任务 → 有库存则生成出库并出补货明细，无库存则 RESTORM 草稿行兜底 → 审计 `MERCHANT_SELF_REPLENISH`。商户小程序「发起补货」页（`pages/self-replenish`）明细按缺货/销量建议预填，提交后直达补货任务。

**门禁**：`scripts/check-merchant-endpoints.mjs` 拒绝式清单钉死 `pages/request`、`replenishment/requests` 字面量（能红已负向验证）；后端端点半边由 check-openapi-types 钉住。上文第 17/21/31/43/50 行关于「要货入口保留/待备货」的表述**就此作废**，勿再引用。
