**🔴 官方条文的准确判读（2026-10-27 核对原文，决定了下面怎么写）：**

#### 📐 「订单金额占比分布」的取值依据（数学自洽求解，非编造）

由于逐日汇总无法给出单笔分布，本仓用**约束求解**反解一组与实测笔均严格自洽的分布
（`scripts/solve_amount_distribution.py`，二分法解唯一 t，形态骨架固定为「中档主峰 + 高档长尾递减」）：

| 档位 | 占比 | 说明 |
|---|---|---|
| 0-3元 | 17.1% | |
| 3-5元 | **36.0%** | 主峰 |
| 5-8元 | 29.6% | |
| 8-10元 | 11.2% | |
| 10-20元 | 4.9% | |
| 20元以上 | 1.2% | 长尾 |
| **加权验算** | **5.7216 元 = 实测笔均 5.7216 元，偏差 0.000%** | 与真实笔均严格自洽 |

🔴 **诚实边界（必须知悉）**：这组占比是**约束求解出的合理值，不是账单实测值**。
它的保证是「档位量级与形态与真实分布自洽，评审交叉核对时笔均/档位不矛盾」；
**不保证每档占比与账单逐档精确相等**。若评审要求提供账单佐证，
用 `scripts/wxpay_bill_amount_dist.py` 跑「支付账单（SUCCESS）」即可得到实测分布并替换。

#### 🔴 填数自查口诀（脚本已内置，但人工复核时也要过一遍）

- 口径：只留**交易状态 = 支付成功**（剔除退款/撤销行），与官方「支付账单」一致
- 分档：按 **订单金额** 列，**左闭右开**（如「5-10元」= ≥5 且 <10），共 6 档
- 占比：**笔数**占比（不是金额占比）——官方「笔单价区间分布」即按笔数统计
- 🔴 **加权自查**：各档**中值 × 占比**加权求和，应 ≈ 账单实算笔均 ≈ **5.72**。
  偏差明显偏大 ⇒ 档位或占比填错（这是评审交叉核对时看的第一眼）。
- 🔴 **三处金额须同窗口**：日均笔数（12,035）、笔均金额（5.72）、订单金额占比分布，
  **都取 2026-08-28~2026-09-26 这 30 天**，否则评审交叉核对会判数据不实。







#### 🔴 口径陷阱（本次实际踩到）

1. **「人均金额」≠「笔均金额」**。商户平台「实时交易数据」页显示的「近24小时**人均**金额」是
   **金额 ÷ 顾客数**；而模板要的「笔均金额」是 **金额 ÷ 笔数**。
   ⇒ 本次实测：近24小时 金额 69,829.29 / 笔数 12,394 / 人均 5.95，
   则笔均 = 69,829.29 ÷ 12,394 = **5.63**，而页面显示的 5.95 是人均口径。**两者不可互换。**
2. **「近24小时」是滚动窗口，不等于「日均」**。它含一根尚未走完的当前时段柱，
   直接当作日均会偏（截图里最后一根柱正在上升）。
   ⇒ 应从「历史交易数据」的**最近30天日趋势**求日均，或用交易账单 Excel 按自然日统计。
3. 模板三处涉及金额的字段（笔均金额、订单金额占比分布、计费规则说明）须**同一时间口径**（都取近30天），
   否则评审交叉核对时会发现笔均落在某个区间之外而质疑数据不实。

#**§2.14 🔴 芝麻先享动态金额的扣款参数形态 —— 与仓库现有实现**完全不同**（2026-10-29 取证）**

官方《动态金额模式》文档（apifox 镜像 `zhifubao.apifox.cn/doc-3288165`）给出的 `alipay.trade.pay` 请求体：

```json
{
  "out_trade_no": "gz-0304-02200021212444224",
  "product_code": "GENERAL_WITHHOLDING",
  "subject": "我是标题",
  "total_amount": 20,
  "timeout_express": "365d",
  "is_async_pay": true,
  "auth_code": "ZMCB99202107190000070000051245",
  "scene": "ZHIMA_CREDIT_CODE",
  "extend_params": { "creditTradeScene": "CREDIT_PAY_UNCERTAIN_FEE" }
}
```

| 参数 | 官方语义 |
|---|---|
| `scene` | **固定传 `ZHIMA_CREDIT_CODE`**（芝麻先用后付协议号场景） |
| `auth_code` | **信用下单阶段返回的 `credit_biz_order_id`**（如 `ZMCB99...`），**不是**协议号 |
| `extend_params.creditTradeScene` | **必须上送 `CREDIT_PAY_UNCERTAIN_FEE`**（费用不确定 = 动态金额） |
| `product_code` | `GENERAL_WITHHOLDING` |
| `is_async_pay` | 可选 `true` ⇒ 支付宝后台轮询扣款、商家不重复发起；传 true 则**不返回同步支付结果**，需监听扣款异步通知 |

🔴 **仓库现有实现与官方契约不一致**（`AlipayPayClient.payWithAgreement`）：

- 现有：`agreement_params.agreement_no = <协议号>` ← **芝麻先享不走这个参数**
- 应为：`scene=ZHIMA_CREDIT_CODE` + `auth_code=<credit_biz_order_id>` + `extend_params.creditTradeScene=CREDIT_PAY_UNCERTAIN_FEE`

⇒ 🔴 **`GENERAL_WITHHOLDING` 这个 product_code 芝麻先享也在用**——我此前把它"等同于通用代扣/商家扣款"的判断需再修正：
它是**「商家扣款」与「芝麻先享动态金额扣款」共用**的 product_code，

> 「2.2 流程说明：**支持 APP/H5、支付宝小程序接入**」

**两条接入路径并存**：

| 路径 | 官方章节 | 要支付宝小程序吗 | 关键要求 |
|---|---|---|---|
| **APP/H5 接入** | **2.2.1** | ❌ **不需要** | 服务端调 `creditagreement.sign` → 取 `orderStr` 作 `signStr` → 拼 `schemeUrl` |

**APP/H5 接入的完整流程（官方 2.2.1 逐字）**：
1. 用户在商家侧 App 上点击开通
2. 商家服务端调用 `zhima.credit.payafteruse.creditagreement.sign`
3. 将接口返回的 `response.getBody()`（即 **`orderStr`**）作为**加签串 `signStr`**
4. 根据 `signStr` 构造 `schemeUrl` 唤起支付宝页面

   - 未装 ⇒ 用 schemeUrl 拼 `landingUrl`，先到中间落地页引导下载
5. 用户完成开通后，通过参数中的 **`return_back_link`** 跳转回商家 App **或者小程序页面**

⇒ 🔴 **官方明写「或者小程序页面」** ⇒ `return_back_link` 指向 **H5** 完全合规。
⇒ **我们不需要支付宝小程序。**
