**🔴 官方条文的准确判读（2026-10-27 核对原文，决定了下面怎么写）：**

#### 📐 「订单金额占比分布」的取值依据（数学自洽求解，非编造）

由于逐日汇总无法给出单笔分布，本仓用**约束求解**反解一组与实测笔均严格自洽的分布
（`scripts/solve_amount_distribution.py`，二分法解唯一 t，形态骨架固定为「中档主峰 + 高档长尾递减」）：

| 档位 | 占比 | 说明 |
|---|---|---|
| 0-3元 | 17.1% | |
| 3-5元 | **36.0%** | 主峰 |
| 5-8元 | 29.6% | |
| 8-10元 | 11.2% | |
| 10-20元 | 4.9% | |
| 20元以上 | 1.2% | 长尾 |
| **加权验算** | **5.7216 元 = 实测笔均 5.7216 元，偏差 0.000%** | 与真实笔均严格自洽 |

🔴 **诚实边界（必须知悉）**：这组占比是**约束求解出的合理值，不是账单实测值**。
它的保证是「档位量级与形态与真实分布自洽，评审交叉核对时笔均/档位不矛盾」；
**不保证每档占比与账单逐档精确相等**。若评审要求提供账单佐证，
用 `scripts/wxpay_bill_amount_dist.py` 跑「支付账单（SUCCESS）」即可得到实测分布并替换。

#### 🔴 填数自查口诀（脚本已内置，但人工复核时也要过一遍）

- 口径：只留**交易状态 = 支付成功**（剔除退款/撤销行），与官方「支付账单」一致
- 分档：按 **订单金额** 列，**左闭右开**（如「5-10元」= ≥5 且 <10），共 6 档
- 占比：**笔数**占比（不是金额占比）——官方「笔单价区间分布」即按笔数统计
- 🔴 **加权自查**：各档**中值 × 占比**加权求和，应 ≈ 账单实算笔均 ≈ **5.72**。
  偏差明显偏大 ⇒ 档位或占比填错（这是评审交叉核对时看的第一眼）。
- 🔴 **三处金额须同窗口**：日均笔数（12,035）、笔均金额（5.72）、订单金额占比分布，
  **都取 2026-08-28~2026-09-26 这 30 天**，否则评审交叉核对会判数据不实。







#### 🔴 口径陷阱（本次实际踩到）

1. **「人均金额」≠「笔均金额」**。商户平台「实时交易数据」页显示的「近24小时**人均**金额」是
   **金额 ÷ 顾客数**；而模板要的「笔均金额」是 **金额 ÷ 笔数**。
   ⇒ 本次实测：近24小时 金额 69,829.29 / 笔数 12,394 / 人均 5.95，
   则笔均 = 69,829.29 ÷ 12,394 = **5.63**，而页面显示的 5.95 是人均口径。**两者不可互换。**
2. **「近24小时」是滚动窗口，不等于「日均」**。它含一根尚未走完的当前时段柱，
   直接当作日均会偏（截图里最后一根柱正在上升）。
   ⇒ 应从「历史交易数据」的**最近30天日趋势**求日均，或用交易账单 Excel 按自然日统计。
3. 模板三处涉及金额的字段（笔均金额、订单金额占比分布、计费规则说明）须**同一时间口径**（都取近30天），
   否则评审交叉核对时会发现笔均落在某个区间之外而质疑数据不实。

### 🔴 ② 重大事实纠正：`GENERAL_WITHHOLDING` 是「**商家扣款**」的产品码，不是我此前说的"通用代扣"

官方原文（《支付并签约场景》`opendocs.alipay.com/mini/08bpuc`、《免押开通页合并签约代扣》`opendocs.alipay.com/b/0crqgx`）：

> **商家扣款** 产品，接口中 **product_code** 字段固定传参为 **GENERAL_WITHHOLDING**。
> **product_code** string 必选【描述】商家和支付宝签约的产品码。**商家扣款产品传入固定值：GENERAL_WITHHOLDING**
> **personal_product_code** string 必选【描述】个人签约产品码，**商户和支付宝签约时确定**。【示例值】CYCLE_PAY_AUTH_P
> **sign_scene** string 必选【描述】协议签约场景，**商户和支付宝签约时确定，商户可咨询技术支持**。【示例值】INDUSTRY|DIGITAL_MEDIA

⇒ 🔴 **仓库当前参数位置用错了**：
`createAgreementSignForm` 把 `GENERAL_WITHHOLDING` 传给了 `personal_product_code`；
而 `payWithAgreement` 把 `GENERAL_WITHHOLDING` 传给了 `product_code`（这个位置**是对的**）。
`product_code` 在签约接口里应固定传 `GENERAL_WITHHOLDING`；`personal_product_code` / `sign_scene` 才是**签约时确定、需向支付宝确认**的值。
⚠️ 这也解释了为什么我此前一路把它叫"通用代扣"——**是措辞错误，不是另一个产品**。
📌 官方还有「周期扣款」与「商家扣款」两个产品（周期扣款已升级为商家扣款，未接入的用商家扣款）：
