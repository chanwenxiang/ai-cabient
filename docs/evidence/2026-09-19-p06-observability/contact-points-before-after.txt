apiVersion: 1

## 改后（工作区：webhook → feishu-alert-relay）
# Grafana 侧告警渠道 —— 与 Alertmanager 复用同一个转换桥。
#
# 为什么不再是 email
# ------------------
# 原先这里是 `type: email` + `addresses: ops@aicabinet.local`，那是个**假地址**：
#   1) `@aicabinet.local` 不是任何可投递的域（保留给 mDNS，公网/内网都没有这个收件域）；
#   2) 全仓没有任何 `GF_SMTP_*` 配置 ⇒ Grafana 根本没配 SMTP，触发即报错；
#   3) 本仓唯一的真实通知渠道是**飞书**（见 alertmanager.yml 顶部的来龙去脉）。
# 三条叠起来 ⇒ 一旦有规则触发，通知必然发不出去，而看板上看不出任何异常。
#
# 为什么指向 feishu-alert-relay
# -----------------------------
# Grafana 与 Alertmanager 都**没有原生飞书 receiver**；两者 webhook 类型发的是各自的 JSON，
# 直连飞书地址会被以 `code=9499 Bad Request` 拒收。桥 `feishu-relay.py` 的
# `render_alert_text` **同时**认这两家的报文（都读 status/alerts[].labels|annotations），
# 因此 Grafana 复用同一个桥即可，**不需要第二个组件**。
#
# 现状（2026-09-19）：Grafana 侧 **0 条 alert rule**。
# 本仓的告警源是单一路径：`infra/prometheus/alert_rules.yml`（22 条）→ Alertmanager
# → 桥 → 飞书。之所以**不**在 Grafana 侧再补一套规则，是因为同一条件两条通道 =
# 同一个飞书群收到两份重复告警，且阈值会分叉。这里保留 contact point + policy，
# 是为了「将来真要加 Grafana 规则时能立刻送达」，而不是暗示现在有规则在跑。
#
# ⚠️ 生效前提：桥在 compose 里挂 `alerting` profile（本机资源有限，不随 dev 栈默认启动），
# 即 `docker compose -f infra/docker-compose.full.yml --profile alerting up -d`。
# 桥没起时，Grafana 的通知会连接被拒 —— 这一点与 Alertmanager 完全一致。
#
# 守这条链路的是 `scripts/check-ops-alert-channels.mjs` 的 R14：
# 假邮箱 / 没 SMTP 却写 email / 断链（服务名·端口·路径）/ policies 里 receiver 悬空 /
# 与 Prometheus 规则重名（双通道重复告警）。
apiVersion: 1
contactPoints:
  - orgId: 1
    name: ai-cabinet-ops
    receivers:
      - uid: ai-cabinet-ops-default
        type: webhook
        settings:
          # 同网络内可解析；必须与 compose 里该服务的 PORT 环境变量一致（R14 会校验有效值）
          url: http://feishu-alert-relay:8098/webhook
          httpMethod: POST
        disableResolveMessage: false

## 为什么它此前永远发不出去（实测）
- 全仓 GF_SMTP_* 命中数: 1
- 收件域 aicabinet.local 是保留给 mDNS 的域，不可投递
- 桥 feishu-relay.py 的 render_alert_text 同时认 AM/Grafana 两家报文 ⇒ 复用同一个桥即可
