# 业务/产品点位信息 · 易购老系统数据导出指引

> 官方依据：《接入支付分须知》(2021-04-06 PDF) 第 14 项
> **「业务/产品点位信息（包括但不限于城市、地址、数量、场景图等）」**
> - 用途：微信支付分申请邮件附件第 5 项
> - 数据源：**易购（easygo）老系统** MySQL（阿里云 RDS）—— 本次拍板用老系统的真实柜机与点位
> - 落档日期：2026-10-27

---

## 一、为什么要走老系统

微信支付分申请附件里的「业务/产品点位信息」必须与邮件里写的经营数据**同源**。
我们邮件里的经营数据（1,109 台柜机、日均 13,686 笔）来自**易购老系统**在收款的交易，
点位也必须取**易购的柜机与点位** ⇒ 数据源在老系统库，不在新系统库。

⚠️ 本仓 `scripts/export_payscore_sites.py` 查的是**新系统**的 `device_info`/`site_contract`，
**在老系统上没有数据**，本轮改用下面的新脚本。

## 二、三步做完

### 第 1 步：在阿里云 DMS 跑一条 SQL（一次导出全部柜机）

SQL 已备好：**`docs/sql/easygo_payscore_sites_export.sql`**

操作：
1. 打开阿里云 **DMS** → 选 easygo 库（老系统 prod 库 `easygo`）
2. 新建 SQL 查询 → 粘贴该文件内容 → 执行
3. 结果集右上角「**导出文件**」→ 选 **CSV** → 下载

这条 SQL 一次返回**全部在册柜机**的点位（城市/地址/经纬度/线长/负责人/**已有点位照片**），
不用一台台跑（老系统 `cabinet_analysis` 里那套是「一柜一跑」9 条，别用）。

> 💡 想只要在线运营的柜机：在 SQL 的 `WHERE` 里加一行 `AND m.online = 1`。
> **建议用全量在册**——官方要「已覆盖点位数量」，在册更保守可信。

### 第 2 步：转成官方要求的 13 字段表格

```bash
python scripts/easygo_sites_to_payscore_table.py <上一步导出的.csv>
```

产出 3 个文件（在 `docs/figures/`）：
| 文件 | 内容 |
|---|---|
| `payscore-sites.csv` | **官方 13 字段表格**（Excel 直接打开） |
| `payscore-sites.md` | 评审用清单（点位汇总 + 设备明细 + 待补项勾选） |
| `payscore-sites-pending.csv` | **地址缺失的柜机**（需人工补地址与城市） |

脚本自动做：按「地址+点位名称」聚合点位、同址多台合并成一行、柜机数量统计、
城市提取（含带省前缀的地址兜底）、柜型映射、**场景图文件名按「序号_柜子编号.jpg」生成**。

### 第 3 步：整理场景图

🔴 **好消息：老系统库里已有「点位照片」字段**（`position_pic_name` / `position_pic_mobile`），
导出表里就有 ⇒ **不用重新拍 1109 个点位**。

做法：
1. 从导出表的「点位照片PC / 点位照片移动端」两列批量下载图片
2. 按点位表里的「场景图文件名」列重命名（如 `001_EGBD06087599.jpg`）
3. 图片与点位表放同一目录，一一对应
4. **缺失的点位再补拍**：画面含柜机全貌 + 摆放环境 + 周边参照物（门牌/工位号/招牌）

## 四、三个必守的规则

1. **一个物理点位一行** —— 同址多台柜机合并成一行、柜机数量填实际台数
2. **场景图文件名与表格严格一一对应** —— 表写 `001_xxx.jpg`，图就叫这个名
3. **柜机数量合计 = 设备照里的柜机总数** —— 两份附件评审最容易交叉核对，数字必须一致

## 五、已验证

脚本用**按老系统导出格式构造的 40 台测试数据**实跑验证（造数→跑→守恒校验）：
- 点位聚合：40 台 → 20 个点位（**35 台有地址 + 5 台待补 = 40，守恒 ✅**）
- 输出列数 = 官方 13 字段 ✅
- 场景图文件名生成、柜型映射、城市提取（含「广东省深圳市…」带省前缀兜底 ✅）均正确

⚠️ 过程中抓出并修掉一个真缺陷：城市兜底正则 `^.{2,4}?(市|…)` 遇「**广东省**深圳市…」会误取"广东省"，
已改为「先剥省级前缀再取市/州」。
