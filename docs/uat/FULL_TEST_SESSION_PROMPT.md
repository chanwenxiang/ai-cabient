### 5.5 业务线清单与「走到底」纪律（🔴 防漏测的机制，不靠自觉）

> 用户明确点出的失败模式：**一条线中途遇到红，就换下一条线开始测**——于是每条线都只测了前半截，
> 后半截（审批、结算、退款、出账、归档）永远没人碰，这就是漏测。本节把「线」显式化并加纪律，
> 使漏测变成**可核对的账面差**而不是感觉。

 纪律（逐条硬执行）
  R1 **一条线跑到本表「终态」列才打勾**。前半截 PASS 不算这条线完成，台账里该线只能写 `PARTIAL`。
  R2 线上遇 FAIL 的标准动作，按序四步，不得跳步：
     ① 取证（请求/响应/DB 快照/截图/根 commit）→ ② 定级（P0–P3，写进 `FINDINGS.md` 给真实 ID）→
     ③ **不改业务代码**、不绕鉴权/限额/验证码，找**最小绕行**（如换一个不触雷的字段组合、
       用另一条等价入口）继续把这条线推到底 → ④ 绕行也推不动 → 标 `BLOCKED-LINE`，
       并**必须**同时登记「未达终态的尾部步骤清单 + 阻塞项 ID + 解锁条件」。
  R3 `BLOCKED-LINE` **不算完成**。允许切去别的线（避免整轮卡死），但该线必须进
     「未闭环业务线看板」（报告独立一节），并在出终版报告前**回归补完**；
     只要看板非空，总结论只能写 **PARTIAL**，禁止写「测试完成/全部通过」。
  R4 禁止"因为难测/要真凭据/要硬件"就 SKIP。真凭据与硬件类只能标 `ENV-BLOCK` 并写清
     需要用户提供的凭据/设备与替代验证路径；**mock 结果不得写成真渠道 PASS**。
  R5 出报告前「**漏测三查**」，三查不过不许交：
     ① 册条目数 ≡ 台账行数（逐册，见 G9-H1）；
     ② 本表 36 条线**每条都有终态或 BLOCKED-LINE 记录**，缺一条 = 漏测；
     ③ P5 判出的每一个 A 类零写入表，必须能反查到「本表哪条线的哪一步本该写它」+ 对应 FAIL 用例 ID
       —— 反查不到就说明这条线根本没跑到那一步。
